# Local database review evidence — 21 October 2026

The review used only synthetic repository fixtures in a disposable Docker
container with `--network none`, no published ports and no production
connection. The cached image ID was
`sha256:01a6a70e41e6c4467c8f55f6063555ed72db2d6662cd0d571040d42eadaeb6f6`;
the running database reported PostgreSQL 17.5 and PostGIS 3.5.2.

## Findings and corrections

- The fixture loader originally emitted `NULL` identifiers for all vocabulary
  tables and `NULL` canonical unit references. The first insert failed its
  primary-key constraint. Explicit fixture-to-column mappings correct this.
- Subgroup rows sorted before their parent system despite an immediate foreign
  key. Root systems now load first, with stable ordering within each class.
- Empty state-code arrays had no SQL element type. They now use `::text[]`.
- Public SQL views admitted proposed/retired stations, unlike the policy
  engine. Append-only migration `V202610211203` limits both views to public
  active/inactive stations while preserving the approved column projections.

## Executed checks

1. Applied all four migrations in filename order with `ON_ERROR_STOP=1`.
2. Loaded the generated fixture SQL twice. Both loads completed; the fixture
   regression confirmed six stations, 69 originals and four revisions.
3. Executed `queries.sql`: no restricted columns appeared in publication
   views, the station view retained exactly 14 approved columns, and
   `neoserver_pub` held SELECT on the two public views only. Representative
   plans used the station GiST index, the March observation partition and
   the observation revision index. These tiny-fixture plans are not load-test
   evidence.
4. Executed `fixture-regressions.sql`: vocabulary mappings, subgroup parent,
   empty arrays and publication grants passed, as did all 12 combinations of
   three visibility classes and four lifecycle states in both public views.
   The temporary station edits were rolled back.
5. Reapplied the historical view definitions in the disposable database. The
   regression failed for a public proposed station, reproducing the disclosure.
   Reapplied `V202610211203`; the same suite passed.
6. Ran `node database/check.mjs`: six checks passed, including the final view
   lifecycle predicate and deterministic SQL generation of 165 inserts across
   21 populated tables.

The commands for repeating migration, double-seed and SQL regression checks are
in [the database README](../README.md#seeding-a-disposable-database). The review
container was removed afterward.

Actual DWRi database-host qualification, production-size query plans,
institutional identity, durable application repositories, migration/restore
reconciliation and owner approval remain release prerequisites. Local SQL
success does not establish those integrations.
